# Bindings do segtools

Metodologia absorvida do coordenador do Fabber (origem: `fabber/repositorio/.claude/skills/agent-coordination`, lida em 2026-09-26). Aqui é skill NOSSA: evolui pelo nosso uso, sem re-sincronizar por cópia.
O que muda no segtools:

| Conceito da skill | No segtools |
|---|---|
| Launcher do worker | `tools/method/worker/ds-worker-host.sh <task> <prompt>` (host) → `tools/method/worker/ds-worker.sh` (devcontainer `segtools-dev`) |
| Timeline / status | `tools/method/worker/ds-worker-tail.sh <task> [N]` |
| Inbox (correção em voo) | `tools/method/worker/ds-worker-send.sh <task> "<msg>"` |
| Worktree por tarefa | `tools/method/worker/agent-worktree.sh add <task> <tipo>/<task>` (tipo = feat|fix|chore|docs… — o pre-push valida `<type>/<slug>`; nunca `wk/`); depois, NO container: `ln -s /workspace/apps/hub/node_modules .worktrees/<task>/apps/hub/node_modules` |
| Credencial do worker | `DEEPSEEK_API_KEY` no arquivo cifrado do repo (origem 1Password sofon/deepseek); nunca a do Fabber |
| Modelo / esforço | `deepseek-flash` / `low` (Opus coordena e raciocina). **O Pro (`FAST_MODEL=deepseek-v4-pro[1m]`) só quando o dono pede explicitamente NAQUELA tarefa** — pedido anterior não vale para a próxima (02/10: o coordenador lançou o Pro por conta própria e o saldo acabou) |
| Prompts | modelo vivo `worker-prompt-vivo.md` (melhora a cada erro); instâncias em `.cache/prompts/<task>.md` (espelhados no módulo `projects` quando o PROJ-CHANNEL existir) |
| Tracker | **módulo `projects`, projeto SEG = fonte ÚNICA** (virada 26/09, ordem do dono): demanda nova nasce como issue (MCP `create_issue`), despacho via `tools/method/worker/dispatch.sh` (issue+prompt anexado), entrega/revisão como comentário `delivery`/`review` + status `qa-ready`/`qa-done`. `BACKLOG.md` = contingência (só com o canal fora; depois `tools/framework/db/import-backlog.mjs`, idempotente por `meta.backlog_id`) |
| Heartbeat | `ScheduleWakeup` 120–180s com worker vivo; 1200–1800s esperando o dono |
| Watchdog filtrado (01/10) | **Primário:** `Monitor` sobre `wsl -d ubuntu-24.04 -- bash -c 'python3 ~/projects/segtools/tools/method/worker/coord-context.py /mnt/c/Users/pablo/.claude/projects/--wsl-localhost-ubuntu-24-04-home-pablo-projects-segtools --watch --limite 300000 & docker exec -u node segtools-dev bash /workspace/tools/method/worker/coord-watch.sh --intervalo 60 --max-silencio 30; wait'` — só imprime (e só acorda o coordenador) quando há evento de outro ator no canal, rodada de worker que terminou, fila `qa-ready` crescendo, commit novo na `main`, contexto da sessão acima de 300 mil tokens por turno (o `coord-context.py` roda no WSL: o container não vê a pasta dos transcripts) ou 30 min de silêncio. Re-armar ao expirar. Medido em 01/10: 74% dos ciclos por cron terminavam sem ação, ~760 mil tokens relidos cada. O cron abaixo vira **reserva** em intervalo longo (`*/30`), para o caso de o Monitor morrer |
| Watchdog (reserva) | `CronCreate` a cada **30 min** (`*/30 * * * *`) com o **texto canônico abaixo, copiado literalmente**; com worker vivo toda execução = ciclo real; reconfirmar com `CronList` e no painel "Tarefas em segundo plano" do app |
| Texto canônico do watchdog | `WATCHDOG do coordenador segtools (backup do heartbeat). Português sempre. 1) date -u; mostrar horários em BRT (date -u -d '-3 hours'). 2) Confirmar no scheduler (CronList / wakeup pendente) que o heartbeat existe; recriar se faltar. 3) Com qualquer worker vivo: ciclo REAL conforme a skill agent-coordination §4–§5 e os bindings do projeto (ler timeline, auditar, corrigir pela inbox, conferir o board do canal, revisar entregas no disco). 4) Sem worker vivo: despachar o próximo item pronto do canal ou nomear a decisão do dono que falta. 5) Relatório no formato fixo 'Ciclo N — HH:MM BRT'.` |
| Contexto da retomada (§0 passo 0) | `HANDOFF.md` → canal (`list_issues` por status in-progress/ready/blocked; `BACKLOG.md` só se o canal estiver fora) → últimos 30 min da sessão atual em `C:\Users\pablo\.claude\projects\D--onedrive-segtools\<session-id>.jsonl` (o mais recente por mtime) |
| Formato do watchdog / heartbeat (espelho do coordenador do Fabber, 26/09) | Watchdog = PROCEDIMENTO genérico (date/BRT → heartbeat existe? → ciclo real se worker vivo → senão despachar o próximo pronto ou nomear a decisão do dono), sem nome de tarefa. Heartbeat = pode citar os workers do momento (é reescrito a cada ciclo). |
| Devcontainer-first (dono, 26/09) | **Tudo o que for possível mora no devcontainer**; o host é a última opção. Código, testes, git (commit/assinatura/push), `gh`, segredos e dispatch rodam dentro do `segtools-dev`. No host só o wrapper de uma linha (`docker exec`) e o que for impossível lá dentro — e isso vira issue para levar para dentro. |
| Sincronização com o GitHub (dono, 26/09) | O trabalho do dia segue na `main` LOCAL (merge das branches dos workers aqui). **Não** abrir PR por commit. Sincronizar com o GitHub **2 a 3 vezes ao dia**: branch `chore/sync-AAAAMMDD-N` com o estado da `main` local → PR único → merge. O pre-push segue barrando push direto na `main` do GitHub. |
| Economia de tokens (dono, 26/09) | **Opus só despacha e lê resultado.** Investigar, corrigir, rodar teste = worker DeepSeek. Revisão = worker DeepSeek com perfil adversarial; Opus lê o parecer e só revisa ele mesmo se for inconclusivo ou crítico. **Opus só age quando o worker DeepSeek não seria efetivo** (decisão do dono, segredo manuseado pelo dono, correção de 1 linha já conhecida). Subagente Claude (Explore etc.) NÃO é o caminho barato — só se o dono pedir. |
| Método padrão (dono, Fabber 26/09) | Reproduzir/corrigir no REAL local primeiro (1 min) antes de despachar ou esperar um processo longo; nada de usar execução lenta p/ descobrir erro. Despachar tudo que estiver pronto — ficar parado esperando o dono em item já decidido é defeito. |
| Horário no relatório | sempre BRT: `date -u -d '-3 hours' '+%H:%M BRT'` |
| Verde | `task check` dentro do devcontainer; `node tools/framework/layout-check.mjs` |
| MCP no worker (DOGFOOD-A, SEG-65) | o `ds-worker.sh` gera `$CFG/mcp.json` com o servidor `projects` (token do worker); o hook de inbox entrega as notificações da issue `SEG_WORKER_ISSUE` ao worker e dá `ack`. Coordenador lê o canal pelo MCP `projects` (`inbox`/`get_issue`/`comment`) |
| Visibilidade na sidebar do app (correção do dono, 26/09) | (1) **Despachar sempre com `run_in_background: true`** no Bash (`tools/method/worker/dispatch.sh ...`), nunca com `&` dentro do comando — só assim o worker aparece como tarefa na sidebar. (2) Para worker já em voo, abrir um **Monitor** sobre `ds-worker-tail.sh <task> 1` (muda status/commits → evento; `MORTO` → encerra). (3) Depois de **reiniciar o app**, o `CronList` pode listar o watchdog antigo sem ele existir de fato: **apagar e recriar** o watchdog (`CronDelete` + `CronCreate`) e reagendar o heartbeat, sem confiar na listagem |
| Quem move/atribui/comenta (SDD farmega `workflow-and-roles.md`, adaptado 26/09; fluxo PUXADO, 29/09) | **Board reflete o real, sempre.** Coordenador (PO delegado + Scrum Master): refina, fecha a prontidão, move para `ready`, despacha (o `dispatch.sh` deixa a issue na FILA: `ready`, sem dono — criada OU reusada; o coordenador nunca move nem atribui em nome do worker). **Worker (DEV):** PUXA quando começa de fato: `move in-progress` + `assign` a si + comentário de entrada, `progress` a cada ≤5 min, `blocker` + `move blocked` + sem owner quando trava, `delivery` + `move qa-ready` (ou `fixed`, numa correção) + sem owner na entrega. **Revisor (QA):** puxa `qa-ready`/`fixed` → `qa-doing`, comenta `review` PASS/FIX; PASS → `qa-done` (entrega de documentação → `qa-doc-ready`), FIX → `fix-needed`. **`pablo` (PO humano):** puxa `qa-done` → `homolog-doing` e fecha em `done`. **O coordenador não fecha nada.** Item parado sem ninguém trabalhando = `paused` (com condição de retomada), nunca `in-progress`. Cada ciclo confere board × realidade (worker vivo ⇔ `in-progress` com owner) |
